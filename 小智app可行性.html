把小智做成手表上的一个 App

方案拆解与可行性分析 · 目标平台 立创黄山派（SiFli SF32LB52-ULP）· 配套手机端小程序
本文只做分析，不含任何代码改动。所有结论都标了出处，可逐条复核。

先说结论

能做，但「把小智做成手表上的一个 app」这句话里藏着一个必须先解决的硬问题：这块手表没有 WiFi。 它没有 WiFi 芯片，不是「没配好」，是芯片本身没有。所以「手表直接连网找小智服务器」这条路， 在这块板上走不通。所有方案的分岔，都是从「网络从哪里来」这一件事上分出来的。

剩下的部分反而比想象中乐观：音频采集、播放、功放、蓝牙协议栈，当前工程里其实已经开着； SDK 里还躺着一份现成的 BLE 对讲例程，明确支持这块板子，而且它已经用上了 Opus。 也就是说，难的不是「能不能出声、能不能传」，而是「怎么把音频送到网络那头」。

一、「app」这个词，得先拆成三个东西这一步不拆清楚，后面全是白讨论

你说的是「app」，但在这块板子上，「app」有三种完全不同的落法， 工作量差好几倍，而且互相之间不是「慢慢做就能升级过去」的关系——选错了要推倒重来。

理解 实际是什么 代价
① 换个固件 把手表整个刷成官方小智固件。开机就是小智，认不出手表界面了。
官方 78/xiaozhi-sf32 已经支持黄山派，有现成固件包。		 半天上手
但手表功能全没了
② 手表里的一个 app 手表的看时间、2048、手电筒都还在，蜂窝里多一个「小智」图标，点进去能对话。
这应该才是你想要的那个。		 最重
要在手表工程里把音频+网络+协议栈全建起来
③ 手表当话筒 手表只负责「采音 + 放音」，真正的脑子（语音识别、大模型、语音合成）放在手机小程序和服务器上。 中等
但前提是你能接受「必须连着手机」

为什么要先分清 ① 和 ②？因为 ① 看起来「官方都支持了，直接刷不就行了」， 但它和 ② 是两个物种：① 刷完这块表就不再是手表了，你前面为表盘、2048、校时做的所有工作， 在新固件里一个都不存在。① 适合「我就想要个小智音箱」，② 适合「我想要一块能叫小智的手表」。

而 ③ 不是 ② 的简化版，它是另一种架构：把手表的职责砍到最小， 把复杂度和算力都挪到手机上。它值不值得走，取决于你对「必须带手机」这件事的容忍度—— 而这恰恰又和「要不要支持 iPhone」缠在一起，第五节会展开。

二、先摸家底：这块板上现在有什么、缺什么

我把当前手表工程编译出来的最终配置（build_sf32lb52-lchspi-ulp_hcpu/rtconfig.h，350 条宏定义） 逐条筛了一遍。结果和「一块光秃秃的开发板」的印象差得挺远。

已经有的（不用你操心）

能力状态说明
麦克风板载 板子上自带了，不用外接
音频采集链路已开启 RT_USING_AUDIO · BSP_ENABLE_AUD_PRC · BSP_AUDPRC_RX0_DMA（录音走 DMA，不占 CPU）
音频播放链路已开启 BSP_ENABLE_AUD_CODEC · BSP_AUDPRC_TX0_DMA
功放驱动已开启 PA_USING_AW8155 · AW8155_GPIO_PIN=42（3W 功放，驱动已编入）
蓝牙协议栈已开启 BSP_BLE_SIBLES · BLE_GAP_CENTRAL · BLE_GATT_CLIENT · BSP_BLE_CONNECTION_MANAGER
连蓝牙连接管理都有，而且之前校时用的标准时间服务（CTS）也在
内存够用 PSRAM 8MB（0x60000000）· HCPU 片内 RAM ≈511KB · 主代码区 Flash 8MB（当前固件只用 2.57MB）
文件系统 / 界面已开启 RT_USING_DFS + FAT（存录音文件用得上）· LVGL v8 + FreeType 中文

缺的（这些是真正的工作量）

缺口性质说明
WiFi硬件没有 筛过 rtconfig.h，0 个 WiFi 宏；板级配置里也没有。这颗芯片就不带 WiFi。
这是整件事的分水岭。
lwIP 网络栈未编入 当前固件里 LWIP / SAL_ / NETDEV 全为 0。SDK 源码里有，只是没编进来。
WebSocket 客户端有源码 SDK 里躺着 rtos/rtthread/components/net/lwip/lwip-2.1.2/src/apps/websocket/websocket_client.c。
而且它的连接函数签名里直接带 bearer_token 参数——正好是小智协议要的鉴权头。
这是个很好的信号：这条路有人铺过。
Opus 编解码未编入 PKG_LIB_OPUS 没开。但 SDK 的 BLE 对讲例程用了它，且明确支持这块板（见下）。
加密库 mbedTLS未编入 小智服务器是 wss://（加密），没有 TLS 就握不上手。编入它会明显吃 Flash 和 RAM。
回声消除 AEC未编入 麦克风和喇叭同时工作时，喇叭的声音会被自己听到。SDK 里有 WebRTC 的 AEC 模块，没开。
不做 AEC，「边放边说」会失灵（小智支持这种对话模式）。
协处理器（ACPU）52 没有 只有 58 系列才有 ACPU。这块 52 芯片没有，所以 Opus 只能在主核用软件跑， 跟界面渲染抢 CPU。
喇叭要买 麦克风板载，但喇叭没有。板上功放是现成的（3W），你只需要接一个喇叭上去。
这是整份清单里唯一要花钱的硬件，也是最便宜的一项。
一句话总结家底：「说话」和「出声」的能力板子上已经具备，蓝牙也醒着。 真正缺的是「上网」这一环——而这一环缺的原因是硬件，不是配置。

SDK 里那份关键原料：BLE 对讲例程

example/ble/talkback/ 这个例程的价值，比它名字听起来大得多。它的支持列表里明确写着 sf32lb52-lchspi-ulp（也就是你手上这块）。它做的事是：两块板子之间，用蓝牙实时传语音对讲。

它已经验证了什么细节
这颗芯片能实时跑 Opus这是最关键的。如果 Opus 跑不动，整个「手表做客户端」的路线就死了。这份例程证明它跑得动。
需要的开关列得很全CONFIG_BLUETOOTH · CONFIG_AUDIO · CONFIG_PKG_LIB_OPUS · CONFIG_PKG_USING_WEBRTC · CONFIG_WEBRTC_AECM（回声消除）· CONFIG_USING_BUTTON_LIB
照着抄就行，不用自己摸。
真实参数会告诉你代价源码里采样率默认被降到了 8kHz（注释里留着 16kHz），Opus 线程栈给了 32KB。
这两条说明：主核软跑 Opus 是要迁就算力的——8kHz 的音质接近对讲机，不是音乐。
但这里有个坑，对「配合小程序」影响很大： talkback 走的是 BLE 5.0 周期性广播，不是普通的 GATT 连接。README 里白纸黑字写着 「本系统基于 BLE 5.0 周期性广播实现，无需传统的 GATT 客户端和连接管理器功能」。
而手机小程序能做的是 GATT 那一套（连服务、读写特征值），接不了周期性广播。
所以不能直接把 talkback 拿来当「手表↔小程序」的通道——要在手表上另外做一个 GATT 服务， 让小程序连上来。好消息是当前工程里 BLE_GATT_CLIENT 和连接管理器都是开着的， 之前做校时也已经走过一遍 GATT 服务的路，不算从零开始。

要做什么

另外主核要同时扛界面 + Opus + TLS，算力和功耗都紧张。
适合谁
只给安卓用户用，且愿意投入最大工作量

路线 C · 手表当话筒，小程序当大脑

手表只管采音放音，联网交给手机
要做什么
手表侧：做一个 GATT 服务，把 Opus 编码后的音频发给手机， 并接收手机回传的音频播放。不用 lwIP、不用 mbedTLS、不用 WebSocket。
小程序侧：连手表、收发音频、自己连小智服务器（WebSocket）。
网络从哪来
手机自己的 WiFi / 4G。手表根本不碰网络。
要买的硬件
一个喇叭
最大风险

安卓侧还要处理定位权限（不给权限可能扫不到设备）。
适合谁
「我要的是手表上有个小智，手机在兜里当它的网卡，两者都接受」

四、网络这一环，单独说清楚

这一节是整份分析里最要紧的。因为它决定了上面三条路线哪一条值得投入。

为什么「让手表上网」这么难

通常给嵌入式设备联网有三条路：接 WiFi、插网线、用蜂窝模组（4G）。这块手表三条都不通：

  • WiFi —— 芯片没有，硬件层面就没有，没有任何配置能变出来。
  • 网线 —— 手表上没有网口。
  • 4G 模组 —— 可以外挂，但要额外模块、额外天线、额外供电，手表那么点空间和电池基本撑不住。

所以只剩第四条路：借手机的网。而借法有两种，这里就是分水岭：

借法原理iPhone 支持吗
蓝牙 PAN 手机把蓝牙当成一个网卡，共享互联网给手表。手表看起来就像插了网线。 不支持
iOS 无此能力
BLE 中继
（小程序方案）		 不走网络共享。手表把数据通过蓝牙发给手机上的一个小程序， 小程序自己用手机的网络去连服务器，再把结果传回来。 支持
BLE 是 iOS 允许的
这就是「配合小程序」的真正价值

很多人以为加个手机小程序是为了好看、方便操作。不是的。

小程序真正的价值，是在「iPhone 不支持蓝牙网络共享」这堵墙旁边，开了一扇门。 手表走 BLE 把音频交给手机，手机用自己正常的网络去连服务器——全程不需要手机的「网络共享」功能， 所以 iPhone 也拦不住。

反过来说：如果你只打算自己用安卓机，那小程序就是多余的， 直接走蓝牙 PAN（路线 A 或 B 的网络方式）就够了。所以「要不要小程序」这个问题， 本质上等于问你：「这东西只给我自己用，还是要给别人用、包括 iPhone 用户？」

小程序的硬限制（这些不是建议，是平台规则）

限制具体数字对你的影响
蓝牙单包大小默认 23 字节，实际可用 20 字节 音频必须切碎了发。频率要算清楚，否则会卡顿。
能不能调大单包只有安卓能主动申请（米 13 Pro 到 220 字节）
iOS 不让，只能听系统安排		 安卓和 iOS 的传输行为不一样，得分别处理。
切到后台iOS：所有蓝牙读写立即暂停，连回调都不触发 小程序必须一直开着前台。用户切出去看个微信，对话就断了。
请求超时切后台后 5 秒未完成的请求被强制中断 不能靠后台慢慢传。
WebSocket 数量最多同时 5 个 够用，但要记得连服务器只能占 1 个。
服务器地址必须 HTTPS / wss，且域名要备案并加入白名单 这一条决定了你能不能「自己搭服务器」。见下。
代码包大小主包 ≤ 2MB，总计 ≤ 20MB 音频处理逻辑尽量精简，别塞大库。

服务器能不能自己搭？

可以，而且这是这条路上少有的「好消息」。小智设备端的协议是公开的，社区里有现成的服务端实现 （xiaozhi-cpp-server、xiaozhiclaw 之类）， 甚至有人把它接到自己的 AI 助手上。设备侧需要的握手信息很明确：

小智协议要点（设备端视角）

  • 连接方式：WebSocket，连接时带四个头 —— Authorization: Bearer <token>、 Protocol-Version: 1、Device-Id（设备 MAC）、Client-Id（设备 UUID）
  • 握手：连上后先发 hello，声明音频参数。设备端上行是 Opus / 16000Hz / 单声道 / 60ms 一帧；服务器下行回的可能是 24000Hz，设备要能重采样。
  • 对话流程： listen start（开始录）→ 持续发 Opus 帧 → 服务器给识别结果 → tts start → 收 Opus 帧播放 → tts stop。
  • 监听模式：有 auto / manual / realtime 三种。 其中 realtime（边听边说）需要回声消除（AEC）支持——这就是前面说 WEBRTC_AECM 没编入会带来的直接后果。
  • 还能控设备：协议里带 iot 指令（就是 MCP 那一套）， 理论上可以让小智控制手表本身——比如「把亮度调低」。
但「能自建」不等于「自建划算」。小程序那一条硬规矩（必须备案域名 + HTTPS）意味着： 只要你不想用官方后台，就得买域名、做备案、租服务器、配证书。 备案本身就要走流程、要时间。
所以：自己玩 → 直接用官方后台（xiaozhi.me），零成本； 真要做成产品给别人用 → 自建这一步躲不掉，而且它是行政流程，不是技术问题， 得提前把时间算进去。

五、分阶段验证路线

不管最后选哪条路，验证顺序应该是从里往外，而不是一上来就搭完整链路。 理由很实际：这条路上环节多，任何一个环节坏了都可能表现为「没声音」， 如果一起上，你根本不知道该怀疑谁。每加一个新环节，都要保证上一次的成功还成立。

第 0 步 · 先确认「能出声、能收声」

目标：证明这块板的麦克风和喇叭是通的。不碰蓝牙、不碰网络。

怎么做：用 SDK 自带的音频例程 （example/multimedia/audio/record 录音，或 example/multimedia/audio/local_music 放音）。 注意 record 例程的 README 里支持列表只写了 eh-lb525， 没有列黄山派——但它要的几个开关（AUDIO CODEC、AUDPRC、AUDIO MANAGER、FAT 文件系统） 你手上这份工程基本都已经是开的，所以挪过来改配置的成本不高。

判据：对着麦克风说话，录一段再放出来，能听清是自己说的。 听到了，这一步过。
先决条件：得先把喇叭接上。板上功放是现成的（3W）， 但喇叭本身要自己买一个。没接喇叭，这一步没法验。

第 1 步 · 跑通现成的 BLE 对讲，验证「实时音频流」

目标：证明这颗芯片能一边采音、一边压缩、一边无线传、同时还能放音—— 这四件事同时发生，是整个小智方案的算力底线。

怎么做：编译 example/ble/talkback （支持列表明确含 sf32lb52-lchspi-ulp）。按 README，需要两块板子对讲。 如果只有一块板，这一步就设法做完整验证——只能确认它能编译、能起来，听不到对讲效果。

判据：按着 PTT 键说话，另一块板子能听到。且明显感觉不到卡顿或断续。 注意它默认是 8kHz——听起来像对讲机是正常的，不是坏了。
这一步是整条路的试金石。如果对讲都卡，那后面接大模型只会更卡 （因为还多了网络延迟）。它过不了，路线 B 和 C 就要重新想。

第 2 步 · 让电脑听见手表（用现成的 WebSocket 客户端）

目标：把音频送到网络那头，但不碰小智的完整协议，先跑通「连得上、传得动」。

怎么做：SDK 里那份 websocket_client.c 编进来， 在电脑上起一个最简单的接收服务，让手表把 Opus 帧发过来，存成文件，用电脑放出来听。

判据：电脑上存下来的文件能放，而且听得出是你在手表那边说的。
这里会撞上路线分岔。手表要连网，就得先解决「网络从哪来」—— 要么蓝牙 PAN（iPhone 不行），要么走路线 C 让小程序转发。 所以这一步其实就是在逼你选路线。

第 3 步 · 对上小智协议，先只做「说」

目标：接上小智服务器，把手表说的话变成文字回来。先不做播放，只看文字。

怎么做：按协议握手（四个头 + hello），发 listen start， 持续发 Opus 帧，在屏幕或串口上看服务器返回的识别文字。

判据：说「今天天气怎么样」，返回的文字里能认出这句话。 认出来了，说明编码、协议、服务器这一整条对上了。
把「听」和「说」分开验，是因为网络往返 + 音频播放两件事叠在一起时， 出问题根本分不清是传输慢还是播放慢。

第 4 步 · 补上「听」，做成完整对话

目标：加上播放路径，做成一来一回的完整对话。

怎么做：收服务器下行 Opus 帧 → 解码 → 送音频输出。 注意服务器下行可能是 24kHz，和上行 16kHz 不一样，要重采样。

判据：问一句，手表能出声回答，且回答内容对得上问题。
这时才会暴露回声问题：喇叭刚说完话，麦克风立刻把它听进去， 可能触发误识别。要「边听边说」就必须开 AEC（CONFIG_WEBRTC_AECM）， 这也是最费算力的一项。

第 5 步 · 最后才是「做成 app」

目标：把上面跑通的东西，搬进手表工程，做成蜂窝里的一个图标。

怎么做：在蜂窝框架里注册一个新 app，界面沿用你现在这套风格。 交互上要处理几个实际问题：什么时候开始听（按键？点击？还是语音唤醒？）、 音量怎么调、网络断了怎么提示。

判据：点图标进去能用，退出后手表其他功能一切正常 （内存没被吃掉——Opus 栈 32KB 只是个开始，音频缓冲和网络缓冲都要占地方）。
这一步的技术含量其实最低，但最容易翻车。 因为前面各步都是「单独跑」，现在要和界面、其他 app、电源管理一起跑。 尤其低功耗：现在屏幕息屏深睡是调通的，加了常驻的音频和蓝牙之后， 续航会掉多少，必须实测。
关于「一开始就语音唤醒」：小智官方固件支持喊「小智小智」唤醒。但 这块板上没有专用的唤醒芯片，关键词检测要么在主核上一直跑（持续吃算力、吃电）， 要么靠按键触发。建议第一版用「点一下屏幕」或「按一下键」来启动， 把常驻唤醒放到最后再考虑，否则它会从一开始就拖住你的功耗和算力预算。

六、不断反问自己

下面这些是我在推演过程中反复卡住的地方。有些是技术问题，有些是「你到底想要什么」的问题。 其中带「先想清楚」标记的，是如果答不上来，后面几周可能白干的问题。

关于你真正想要什么

「app」到底指哪个？①换固件 / ②手表里的图标 / ③手表当话筒
这三个的工作量差好几倍，而且不能中途升级。先想清楚。 我的猜测是 ②，但你确认一下——如果你其实只想要个能对话的设备，那 ① 是最省事的选择。
这东西是「自己玩」还是「给别人用」？
这一个问题直接决定要不要自建服务器。自己玩→官方后台，零成本。 给别人用→域名、备案、服务器、证书全套上来，而且备案是流程活，不是技术活，要提前排时间。 这两条路的成本差一个数量级。
必须支持 iPhone 吗？
如果答案是「必须」，那小程序中继（路线 C）是唯一的活路， 因为 iPhone 不支持蓝牙网络共享，这条路被硬件和系统双双堵死。
如果答案是「我自己用安卓就行」，那小程序就是多余的，直接走蓝牙 PAN，能省掉一整个环节。先想清楚。
能接受「对话必须开着手机、且手机不能切后台」吗？
走路线 C 的话，iOS 一旦切后台就断蓝牙，回调都不触发。 所以用户得把小程序一直摆在前台，手表才连得上。这体验你能接受吗？
对比一下：手腕上抬起手说话，结果还得先掏手机点亮小程序——这个动作会不会把「手表」的意义抵消掉？
能接受音质像对讲机吗？
talkback 例程默认降到 8kHz，这是为了省算力。小智协议本身要 16kHz。 主核软跑 Opus 能不能稳在 16kHz，我没实测过，不能替你保证。 如果只能跑 8kHz，音质会是「能听懂但发闷」。
响应速度要求多高？
完整链路是：说话 → 编码 → 传输 → 服务器识别 → 大模型 → 合成 → 传回 → 解码 → 播放。 光是网络往返通常就要一两秒，加上大模型思考，答话前静默两三秒是正常的。 这个延迟如果让你觉得「不如直接掏手机」，那这个项目的价值就要重新算。

关于技术上的坑

没有 WiFi，你接受「必须配着手机」这个前提吗？
这不是选择，是硬约束。所有路线都得配手机。 区别只是「配手机干什么」——路线 A/B 让它当网卡，路线 C 让它当前台中继。
蓝牙带宽真的够吗？
小程序 BLE 默认单包可用 20 字节，而且 iOS 不让主动调大。 16kbps 的 Opus 换算下来需要约 100 个包/秒。这个数字和 BLE 的连接间隔叠加之后 到底稳不稳，必须实测，我在这里只能标红，不能给你答案。
如果实测不够，退路是把采样率降到 8kHz（数据量减半）。
Opus 在主核跑，和界面渲染抢 CPU，会怎样？
这块 52 芯片没有 ACPU 协处理器（那是 58 系列才有的）， 所以音频和界面只能挤在同一个核上。
后果可能是：对话时界面动效掉帧，或者音频被界面卡出断续。 这也是第 1 步要用 talkback 先验证的原因——那是纯音频没有界面的最好情况， 真做 app 时只会更差。
内存够吗？PSRAM 8MB 听着很多。
但已经分出去不少了：LVGL 的图片缓存就占了 1.1MB， 再加上 FreeType 字体缓存。Opus 线程栈 32KB 不算大， 但音频缓冲、网络缓冲、TLS 握手时的临时内存都要留。
8MB 写在纸上很宽裕，实际会不会紧，要看编进 mbedTLS 之后的样子，得实测。
续航会掉多少？
现在息屏深睡是调通的。一旦加上常驻蓝牙 + 麦克风 + 音频处理， 深睡基本就没了。具体掉多少我不知道，但「掉得很明显」是可以预期的。 这是手表类设备最容易被低估的一项。
回声：喇叭的声音被自己麦克风听进去怎么办？
SDK 里有 WebRTC 的 AEC 模块但没编入。 不做 AEC，「边放边说」这种对话模式会失灵，只能做成「按一下说一句」的回合制。 回合制体验差一些，但省算力——这是个可接受的降级方案。
talkback 走的是 BLE 广播，不是 GATT，小程序连不上，怎么办？
这是我在读 README 时发现的一个隐蔽问题：talkback 用的是 BLE 5.0 周期性广播，而小程序只能做 GATT 那一套，接不了广播。
所以路线 C 要另外写一个 GATT 服务。 好消息：当前工程里 GATT 相关开关都开着，之前做蓝牙校时已经走过一遍这条路， 不是从零开始。
我是不是在用「开发板的可行性」替代「产品的可行性」？
这是我最想提醒自己的一点。「技术上做得到」和「做出来好用」是两回事。 前面所有分析证明的都是前者。后者取决于：延迟能不能忍、音质能不能忍、 续航能不能忍、还有那个「必须掏手机点亮小程序」的动作能不能忍。
这几件事没有一件是我能替你判断的。

七、如果让我给一个建议

别急着写代码。先花最小的代价把最大的不确定性打掉。具体就两件事：

  1. 买个喇叭接上。这是整份清单里唯一要花的硬件钱，也是所有验证的前提。 板上功放是现成的，接上就能用。
  2. 编译跑通 example/ble/talkback。 它明确支持你手上这块板，是「这颗芯片到底能不能扛实时语音」这个问题的唯一权威答案。 如果能过（哪怕只有一块板，先确认能编译、能起来、日志正常）， 那路线 B 和 C 就是"难"而不是"不可能"；
    如果卡住了，说明问题出在算力或音频链路上——那这时候再谈接大模型、谈小程序，都是空中楼阁。

这两件事都不需要改现有手表工程一行代码，不影响你已经做好的表盘、2048、校时。 做完再决定走哪条路线，比现在拍脑袋选一条要踏实得多。
