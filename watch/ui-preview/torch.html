手电筒 App：灯不亮的真凶找到了

你两次反馈轻触点不亮。第二次我没再猜 app 代码，改成先证明"你的点击到底有没有送到"—— 结果送到了，一次不落。真正的病根是 proj.conf 里一个编译宏名抄错： 写成 ..._CC1_USING_DMA，正确是 ..._UPDATE_USING_DMA。 差这一个词，PWM 的 DMA 句柄就是空的，而驱动在句柄为空时照样返回"成功"， 于是串口全绿、灯却从来不亮。已修，正在重编。

轻触现在是三档循环

LED 关屏幕还是亮的，只是背面那颗小灯不亮
LED 常亮满白长亮，约 60mA
LED 频闪5Hz（100ms 翻一次）

进 app 默认就是常亮 —— 手电筒进来就该亮，不该还要点一下。 所以第一次轻触是切到频闪，不是"开灯"。

为什么轻触不用 LV_EVENT_CLICKED

CLICKED 是 LVGL 自己在一串条件都满足时才合成的：按下命中、没被滚动接管、 抬起与按下还是同一对象……这条链上任何一环被别的对象插一脚，事件就静默不触发， 而且从代码上完全看不出来，现象只是"点了没反应"，没法往下查。

现在自己收 PRESSED / RELEASED： 位移 < 24px 且时长 < 1.2s 才算一次轻触。 好处是每次按下抬起都会打一行日志（torch: evt PRESSED x=195 y=300）， "事件到底到没到"一眼可判；顺带把"手指划一下也被当成点击"这种误触一起挡掉。

屏幕不会自动熄灭

watch_demo.c 里那个 30ms 一次的定时器，只要 lv_disp_get_inactive_time() > 10s 就 gui_pm_fsm(SLEEP)。 手电筒恰恰是"开着不动"的用法 —— 不挡就是 10 秒后自己黑掉。 做法是起一个 1s 的 lv_timer 反复 lv_disp_trig_activity()， 不用去改 watch_demo.c 那套 PM 逻辑。

真凶：一个编译宏名抄错 差一个词，灯全黑

先把上一轮"软件全绿、剩硬件"的结论撤掉——那句话是我误判。 这次不猜代码，先回答一个更基础的问题：你点屏幕，事件到底有没有送到 app？ 用 tp_ctrl click 从触摸驱动层注入一次真点击（走完整 LVGL 输入通路，不是绕过）， 串口立刻打出：

torch: evt PRESSED(1) x=195 y=300 torch: evt RELEASED(8) x=195 y=300 torch: release dx=0 dy=0 dt=96ms -> TAP torch: led mode=2 (0=off 1=on 2=strobe) ret=0 found=1

事件到了、判定过了、模式也循环了（连点三次 mode 走 1→2→0→1）。 所以你看到的"没反应"，从来不是触摸的问题 —— 是灯根本就没亮过， 而灯不亮的反馈只有一颗小小的光点，看起来就像"点没生效"。

现象说明什么怎么判
点下去一行日志都没有 触摸没送到这个界面（命中失败 / 被别的对象吃掉） torch_act 看 indev 内部状态与真实命中
有 PRESSED 没有 RELEASED 手指被 PRESS_LOST 抢走了 日志里会直接打 PRESS_LOST
有 release … -> TAP 但灯不亮 触摸这层已经清了，往驱动/编译配置走 看 ret=——但见下方警告，它不一定是真的
tp_ctrl click 195 300 也没反应 才是触摸驱动/校准层的问题 这一条比手点更干净：坐标固定、时序确定

病根链条：为什么"返回值 0"是个假绿灯

写 WS2812 只认 rt_device_find("rgbled") + PWM_CMD_SET_COLOR， 一路都是 RT_EOK。但往驱动里点进一层就发现：

事实含义
drv_rgbled.c 写死 config.dma_type = 0 驱动去取 pwm->pwm_update_dma 这个句柄
只有 #ifdef BSP_PWM3_UPDATE_USING_DMA 才给它赋值 我的 proj.conf 写的是 ..._CC1_... → 这个宏压根没定义
句柄是 NULL，但 PWM_CMD_SET / ENABLE 照样返回 RT_EOK 返回 0 只证明"调用被受理了"，不证明硬件动了。这才是死结所在
教训：驱动返回值 ret=0 不能当作"硬件真的动了"的证据； "我的代码和官方例程一字不差"也不是——配置文件没一起比，就等于没比。 官方例程的 proj.conf 里明明白白写着 UPDATE，我当初是照字面猜成 CC1 的。

改了什么

  1. project/proj.conf 第 155 行： CONFIG_BSP_PWM3_CC1_USING_DMA → CONFIG_BSP_PWM3_UPDATE_USING_DMA。 这是唯一的实质修复，其余都是为了看清它而加的取证。
  2. 轻触改手写判定（不再用 LV_EVENT_CLICKED）： 自收 PRESSED/RELEASED，位移 < 24px 且 < 1.2s 才算一次轻触。 好处是每次动作都有日志，把"没反应"从黑盒变成可读的一行 —— 上面那段 evt PRESSED / RELEASED 就是它打出来的。
  3. LDO + pinmux 每次点亮都重做：原来用一个 s_led_ready 做成只跑一次， 但休眠会关掉灯珠的 LDO3_3V3、也可能把 PA32 从 GPTIM2_CH1 复位回 GPIO。 现在 find 设备只做一次，供电和引脚复用每次重做。
  4. 驱动返回值记进 last_ret：不再丢掉， torch_info 一行可见 —— 虽然这一轮证明了它不能单独当证据， 但"丢了更没法查"。

顺带说清：颜色是 8bit/通道

从驱动实现里确认：red = (color & 0x00ff0000) >> 16，逐位映射成 PWM 占空比。 所以 SDK 例程那个 0x0f0f0f 只有 6% 亮度 —— 当氛围灯够、当手电筒远远不够， 满白必须是 0xFFFFFF。

光有两个来源 别只做屏幕那一个

屏幕 主光源

  • 整屏纯白（#FFFFFF）+ 背光 100%
  • 纯 LVGL，不需要任何编译开关
  • 面积最大、真能照东西
  • 靠 1s 定时器顶住 10s 自动息屏

WS2812 小灯 辅助光源

  • 板子背面那颗，挂在 PA32 / GPTIM2_CH1
  • 点光源，颜色 0xFFFFFF 满白
  • 要开 5 个编译开关（见下）
  • 电源和引脚复用每次进 app 都要重做

⚠ 四个容易漏的前提（漏一个就"串口全绿、灯不亮"）

  1. 配置里那个 DMA 宏必须是 UPDATE 而不是 CC1。 这才是这次真正踩到的坑，也是最难发现的 —— 它不在 .c 里， 编译器不报错、运行时不报错、ret 还是 0。 写成 CC1 时 rgbled 要的 DMA 句柄是空的， 驱动会静默退回到"不带 DMA 的普通 PWM"，于是 WS2812 的时序根本没发出来。
  2. 灯珠是片上 LDO3_3V3 供电的。必须 HAL_PMU_ConfigPeriLdo(PMU_PERI_LDO3_3V3, true, true)， 否则怎么设颜色都不亮，而代码看起来完全正确。
  3. PA32 默认不是 PWM 脚。板级 bsp_pinmux.c 把它初始化成了 GPIO_A32（下拉），要自己重新映射成 GPTIM2_CH1，WS2812 的时序才有地方出来。
  4. 颜色是 8bit/通道，不是 4bit。驱动里是 red = (color & 0x00ff0000) >> 16， 所以 SDK 例程那个 0x0f0f0f 其实只有 6% 亮度 —— 当氛围灯够，当手电筒不够。 满白是 0xFFFFFF。
第 2、3 条不是"配置一次就完"的，是"每次进 app 都要重做"的。 这点很容易漏 —— 见上一节。
第 1 条正相反：改一次就一劳永逸，但它藏在编译配置里， 改错了没有任何报错，只有"灯永远不亮"这一个现象。

要加进 project/proj.conf 的 5 行

CONFIG_BSP_PWM3_UPDATE_USING_DMA=y CONFIG_RGB_SK6812MINI_HS_ENABLE=y CONFIG_RGB_USING_SK6812MINI_HS_DEV_NAME=y CONFIG_RGB_USING_SK6812MINI_HS_PWM_DEV_NAME="pwm3" CONFIG_BSP_USING_RGBLED_CH=1

五行照抄 SDK 给这颗芯片的现成例程（watch/ws2812/ 与 example/rt_device/rgb_led/，对本板取值一致）。 第一行是这轮的真凶：我原先写成 ..._CC1_USING_DMA，而例程里是 UPDATE。 两者的区别是"DMA 由定时器的哪个事件触发"—— UPDATE 是周期更新事件、CC1 是通道比较事件； 而 rgbled 驱动走的是更新事件那条路，写成 CC1 这个宏就等于没开，句柄是空的。

规则：配置名一律照抄官方例程，不要凭字面猜。 CC1 看起来"更像 PWM 一点"，但驱动要的是 UPDATE。 猜错的代价是编译器不报错、运行时不报错、串口全绿、灯全黑 —— 最难受的一类错。

另外：..._DEV_NAME 那行才是注册设备名的开关 —— 不开它，驱动里 RGBLED_NAME 都不存在，rt_device_find("rgbled") 永远返回空。 PWM2 被 LCD 背光占着，所以用 PWM3。

能自动验的 vs 只能靠眼睛的 先说清楚边界

「灯到底亮没亮」屏幕截不到、串口看不见，最后一步只能靠人眼。 但这不代表整条链路都只能靠眼睛 —— 下面这些都能从串口读出来：

命令 / 观察点验的是什么
torch_info 一行总览：on / mode / saved_bright / led_found / last_ret（驱动返回值）/ strobe_timer / root x=… clickable=…
torch_hit 195 300 问"这个坐标点下去会命中谁"。 回 ROOT(good) = 事件一定能送到；回 OTHER / NOTHING = 被挡了或尺寸不对
torch_act（本轮新增） 拆触摸黑盒的主力：把 LVGL 输入设备内部状态全打出来 —— type / state / disabled / raw·act·last 三个坐标 / rot·offset / act_obj·last_pressed， 再用 LVGL 自己的 lv_indev_search_obj() 做一次真命中测试， 打印 real-hit FINAL=… is_root=…。 这一条就能把「事件没到 / 被别的层挡 / 触摸没进 LVGL」三种原因分开
torch_tree（本轮新增） 递归打印 layer_top / layer_sys / scr 下面的对象树 （WxH at(x,y) clk/hid/opa + 缩进）。 用来确认"屏幕上到底压着什么"—— 本轮就是靠它看到 layer_top 上那个 20×450 的左边缘手势条，确认它不挡中间
tp_ctrl click 195 300（SDK 自带） 端到端验输入通路：从触摸驱动层注入一次按下+抬起， 走完整 LVGL 输入通路（和手点等效），比 torch_tap 更硬 —— torch_tap 是直接调 app 的判定函数，跳过了触摸这一层
torch_tap 模拟一次轻触，走的是和真手指完全同一条逻辑。 它有效而手点无效 → 触摸路径的问题；它也无反应 → 逻辑的问题。把两类原因分开
torch_strobe / torch_strobe 0 直接进/出频闪模式，不看触摸
torch_raw FF0000 现场试灯用：直接写任意颜色（红色在满白背景下最容易看出灯亮不亮）。 回 raw 0xFF0000 -> ret=0。
⚠ 它会把 mode 置成 0（故意的：手动试色要退出模式循环， 否则会被频闪定时器立刻覆盖）。所以 torch_info 里 mode=0 不代表灯是灭的，别被这一行误导
torch_comp 0|1 切驱动结构体里的 is_comp 字段并立刻重写一次颜色，用来对比亮度差异
torch_evt 0|1 触摸事件日志开关（默认开）。按下/抬起各打一行坐标，稳定之后可以关掉
torch_led 1 / torch_led 0 强制常亮 / 灭。不带参数 = 按轻触的循环走一格
torch_on / torch_off 背光存/还的往返：ON backlight=100 (saved N) → OFF backlight restored to N
torch_ui 从串口直接进这个 app（照 to_clock 那套 gui_app_run()）。 没有它，「界面建没建 / 防息屏定时器起没起 / 退出还背光没」三件事一条都验不到
calc_menu 遍历框架内置 app 列表，确认 torch 真的落在蜂窝某一格 （icon 为 NULL 的 app 不会进蜂窝，这是最常见的坑）
物理上那颗灯亮不亮只能靠人眼。这才是真正需要你确认的一项
⚠ 切换动作必须走 lv_async_call 派回 GUI 线程。 串口命令跑在 shell 线程，直接在里面碰 LVGL 会撞 CHECK_CUR_RTOS_TASK() 的断言 —— 和 swipe_sim 同一个理由。 只读的诊断（torch_info / torch_act / torch_tree / torch_hit）可以直接调。

万一还是不亮：按顺序量两个电压

  1. 万用表量灯珠 VDD 对 GND → 期望 ≈3.3V，验 LDO 有没有上电。
  2. 万用表量 PA32 对 GND → 直流档读到的应是脉冲均值，约 0.8~1.7V。 量不到 0.8V 以上就说明引脚没输出。
  3. 上面两步都正常但灯不亮 → 灯珠本体 / 焊接 / 方向（SK6812MINI 有方向标记）。

⚠ 别用万用表去"看"WS2812 的数据波形（800kHz 脉冲）—— 量不出来，只能量直流均值。

顺带记一个编译坑：MSH_CMD_EXPORT(fn, desc) 的描述里不能有逗号 —— 会被预处理器当成参数分隔符，报成「passed 4 arguments, but takes just 2」， 看着完全不像逗号的问题。描述里逗号统一换成 /。
