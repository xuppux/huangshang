## 一、这个工程是什么

思澈（SiFli）官方的 **LVGL 手表 UI 示例**，立创做了定制版（本工程就是从立创的
`lckfb-hspi-ulp_example` 仓库拉下来的）。

**先说清楚它不是完整的手表系统。** 它有漂亮的界面框架，但底下没接数据：

| 界面做了 | 但实际是 |
|---|---|
| 蜂窝主菜单（**59** 个图标位） | 其中只有 **3 个是真应用**，其余 56 个点进去没反应 |
| 多套表盘 + 动态加载 | **时间是假的** —— 用 `clock()`（CPU 计时），开机从 00:00:00 走 |
| 下拉面板 | 是**开发者调试面板**（调重绘间隔的滑块），不是控制中心 |
| 3D 立方体转场 | 真的在转，但转的是 `d3d_rotate` 那张**红叉测试图** |

**它的价值在框架，不在功能。** 想直接拿一个"能戴的手表"来用，看的是
`Gangan-307/LCHSP_Watch`，不是这个。

那为什么还要它？因为它是**官方骨架 + 带完整教程**，学"手表固件怎么分层"比
一个功能齐全但结构复杂的项目更适合起步。

> **顺带查出来的两个坑**（详见第四、五节）：
> ① 蜂巢里那 56 个占位图标，**14 张图里有 8 张资源文件是坏的**（内容是「思澈科技」的字形）；
> ② 官方 PC 模拟器需要 MSVC，这台机器上没有。

### 编译

**双击 `watch\build.bat` 就行。** 三层其实是同一件事：`build.bat` → `build.ps1` → `build_py.py`，
真正干活的只有 `build_py.py` 一个文件。

```powershell
.\build.ps1                 # 编译黄山派固件
.\build.ps1 -Clean          # 先清理再完整编译
.\build.ps1 -PcSim          # 编译 PC 模拟器版（在电脑上跑 UI，不用烧板）
```

**为什么绕到 `build_py.py`：**

1. 它不依赖 shell 传递环境变量 —— 在自己的 Python 进程里把 `os.environ` 和 `sys.path`
   都设好，再直接调 `SCons.Script.main()`。官方 `export.ps1` 那条路会踩到：
   `ModuleNotFoundError: No module named 'building'`、
   `TypeError: expected str, bytes or os.PathLike object, not NoneType`、
   以及环境激活后 `PATH` / `PYTHONPATH` 莫名丢失。
2. 它带一个**必须打在 Python 进程里**的补丁（下面「已修的两个坑」第 ② 条）。

`build.ps1` 只在找不到虚拟环境 Python 时才回退到 SDK 官方的 `export.ps1` + `scons`。

**首次编译实测约 23 分钟**（LVGL v8 全量 + 12 个巨型字体数组）。
增量编译快得多：全量编过一次后，只重新生成链接脚本那一步实测 **43 秒**。
编译日志：`build_py.log`。

#### 已修的两个坑（都很误导人）

**① 中文路径 —— 链接器"看不见"SDK**

```
ld.exe: cannot find -lhal_epic_ex_gcc: No such file or directory
```

库文件明明就在 `sifli-sdk\drivers\hal_epic_ex\libhal_epic_ex_gcc.a`。
原因是：链接命令太长时，SDK 会把参数写进**响应文件**（`@file`）再交给 `ld`，
而响应文件里的中文在这条链路上会被破坏。又因为 `-L` 里**只有 SDK 是绝对路径**
（目标文件、链接脚本都是相对路径），所以**只有这一个库**报错，极具迷惑性。

对照实验：同样的响应文件机制下，ASCII 路径能找到库，中文路径找不到
（UTF-8 / GBK / MBCS 三种编码都试过，全挂）。

→ 外层文件夹必须纯英文（现名 `huangshanpai`）。两个脚本都加了非 ASCII 预检查。

**② 并行编译的 `PATH` 竞态 —— 报"找不到编译器"**

```
Error in calling command:arm-none-eabi-gcc
Exception: No such file or directory
Please check Toolchains PATH setting.
```

工具链完好。问题在 SDK 的 `tools/build/building.py`，`Win32Spawn.spawn()` 是这么干的：

```python
old = os.environ['PATH']
os.environ['PATH'] = env['ENV']['PATH']     # 临时改写【整个进程】的 PATH
subprocess.Popen(cmdline, env=env)          # Windows 靠父进程 PATH 找 exe
os.environ['PATH'] = old
```

`-j8` 时 8 个工作线程共用这一个进程级全局变量。实测抓到的记录：进程 `PATH` 在
**4533 / 387 两个值之间反复跳**；而且 `finally` 恢复的是"自己进来时看到的值"，
可能已经是别的线程写的值 —— 于是 `PATH` 会漂移。某次漂到不含工具链的版本，
`CreateProcess` 就返回 WinError 2，编译器"凭空消失"。

→ 已在 `build_py.py` 的 `_harden_spawn()` 里修掉：把编译器先解析成**绝对路径**再调用，
正常路径下不再碰进程 `PATH`（**不改 SDK 文件**）。日志里会打印一行 `[加固] ...`。

产物在：

```
C:\Users\18058\Desktop\huangshanpai\watch\lvgl\watch\project\build_sf32lb52-lchspi-ulp_hcpu\
```

**已实测的产物**（2026-09-20，0 error 0 warning）：

## 四点五、蜂巢菜单到底是怎么拼出来的

看 `src/gui_apps/main/app_mainmenu.c`，`app_mainmenu_read_app_icons()` 分两步填格子：

**第一步：真应用**（链接顺序来自 `main.map` 的 `BuiltinAppTab` 段）

```
0x120c0900  app_clock_main.o        → idx 0（钉死在正中心）
0x120c091c  LC_Hello_World/main.o   → idx 1
0x120c0938  app_mainmenu.o          → 跳过（它自己就是菜单）
0x120c0954  rotation3d.o            → idx 2
```

所以 **idx 0 = 时钟、idx 1 = 立创 Hello World、idx 2 = 旋转立方体**，就这 3 个。

**第二步：占位凑数** —— `app_mainmenu.c:1176` 有个
`#if 1 //for demo, full fill screen`，里面硬编码了一个 **56 项的图标数组**，
用同一批 14 张图循环贴 4 遍，命令字全写成 `"none"`（点了没反应），
还额外加 `lv_obj_set_style_img_opa(..., LV_OPA_50)` 变成半透明。

**结论：59 个图标里 56 个是纯装饰。** 这是判断这份工程"是骨架不是成品"最直接的证据。

## 五、已知限制

**① 冷启动后时间不对 —— 已定位，是硬件限制不是 bug（2026-09-20 实测）。**

先说结论：**RTC 整条链路都是好的**，缺的只是"断电后从哪拿时间"。

- 表盘和 `rtc_now` 命令都走 `time()` + `localtime()`，直接读 RTC 硬件，
  每 1 秒重新问一次，所以 **`show_date` 改完时间 1 秒内屏幕就变**，不用重启表盘。
- 实测走时：`clkdiag` 自检每 2 秒采样，秒数精确 +2，连跑 60 秒无跳变。
  开机日志里的 `I/drv.rtc main: RTC use LXT` 说明用的是板上那颗 32.768 kHz 独立晶振。
- **RTC 值能不能留住，只取决于供电**，看开机横幅那行 `Serial PowerOnMOde:`：

  | 场景 | 标志 | RTC 值 |
  |---|---|---|
  | 软复位 / reboot / 重新烧录 | `PowerOnMOde:4` | ✅ **保持**（实测 19:09:22 → 19:09:57） |
  | 单片机睡眠 | —— | ✅ 保持 |
  | **拔 USB 再上电** | `PowerOnMOde:0` | ❌ **归零**（`rtc at boot: 2000-01-01 00:00:00`） |

- **根因：这块板子的 RTC 域没有备份电池**，拔电即丢时。
  （`bsp_power.c` 里有完整的 VSYS / VCC_3V3 / GS_3V3 电源路径管理，但那是主电源，
  不是给 RTC 域单独供电的。）

**于是"看着像时间坏了"是四件事叠出来的，没有一件是 bug：**

1. 冷启动 RTC 归零；
2. `app_watch_entry()` 会给它兜一个 `2024-01-01 12:00`，
   而**这个值长得像个正常时间** —— 屏幕上一句"12:00"，不像坏也不像没设；
3. 表盘只有 HH:MM 没有秒，且**只在分钟变化时才重画图像源**（省电），
   所以一分钟之内画面是**完全静止**的；
4. 10 秒无操作就息屏，用户几乎看不到它翻到下一分钟。

→ 合起来就是「时间一直是 12」。**用户的原话「断开就不运行了」是对的。**

**现在的处理：**

- 表盘上加了「**未校时 · 请重新对时**」琥珀色提示（`RTC_SET_MIN_YEAR=2025`，
  年份小于它就亮出来），把"为什么是 12"直接讲明白，不再让人猜。
- 冒号改成每秒闪一下（`WF_COLON_BLINK 1`），让"表盘还活着"肉眼可见 ——
  否则"静止"和"卡死"根本分不出来。
- **校时**：串口敲 `show_date 2026 9 20 19 30 0`（年 月 日 时 分 秒），
  或跑 `.\serial.ps1 -SetTime`（用这台电脑的钟）。不带参数是查看。
  `.\build-and-flash.ps1` 默认烧完就自动校时。
- **根治要外部时间源 → 下一步做蓝牙（BLE）校时。**
  SDK 里已有 `BSP_BLE_TIMES`（时间服务）/ `BSP_BLE_TIMEC`（时间客户端）。
  可选过渡：把上次已知时间存进 NOR flash，冷启动恢复（日期大致对，误差 = 断电时长）。

`app_clock_main.c` 里那个 `clock()`（CPU 周期计数）只给框架自带的
`simple` / `dial` 表盘用，它们会在 `on_start()` 里快照一次时间再靠 tick 累加 ——
**自己写的表盘不要走那条路**，直接用 `time()` + `localtime()`。

**② 下拉面板不是控制中心**，是调试滑块（重绘间隔 1–3000ms），而且事件回调被注释掉了，
拖了没反应。

**③ Flash 空间。** 分区表铺到 `0xC28000` ≈ 12.7 MB，主固件已占 2.6 MB。
用 `df /` 看剩余空间。文件系统是 **ELMFAT（FAT）**、扇区 4096 字节
（早先写的「LittleFS」是错的 —— `rtconfig.h` 里只有 `RT_USING_DFS_ELMFAT`）。
Flash 颗粒容量待确认：`rtconfig.h` 写 32 MB，板子资料写 16 MB，两者不一致。
详见 `..\硬件实现清单.md`。

**④ 板子上没有的器件：** 心率血氧 PPG、GPS、NFC、振动马达本体
（只有驱动电路和预留焊点）。要加心率得自己选一颗 MAX30102 走 I2C 接上去。

**⑤ 官方 PC 模拟器暂时用不了。** SDK 有 `project\pc_hcpu\` 和 `--board=pc` 目标，
但 `customer\boards\pc\hcpu\rtconfig.py` 写死 `CROSS_TOOL='msvc'`，
`msvc_setup.bat` 还要求 `VS2017\...\MSVC\14.16.27023` +

**① `middleware/bluetooth` 是 submodule，必须单独拉**

这是这份 SDK 最容易漏的一步。`.gitmodules` 里声明了：

```
middleware/bluetooth  ->  ../SiFli-Bluetooth.git
```

目录**存在但是空的**（0 个文件），而 `middleware/Kconfig` 第 13 行无条件写
`rsource "bluetooth/Kconfig"` —— 于是 kconfig 一解析就崩：

```
AssertionError: Fail to generate .config and rtconfig.h
```

修复：

```bash
cd C:\Users\18058\Desktop\huangshanpai\sifli-sdk
git submodule update --init middleware/bluetooth     # 拉到 959 个文件
```

> 教训：**遇到「Kconfig 找不到 X」先查 `.gitmodules` + 那个目录的文件数。**

**② SDK 自带的 `export.ps1` 在 Windows 上有大小写 bug**

```
"powershell.EXE" shell is not among the supported options
```

它探测父进程名得到 `powershell.EXE`（大写 .EXE），白名单里却只有小写。
绕过办法是显式指定（`build.ps1` 里已经这么做了）：

```powershell
$env:SIFLI_SDK_SHELL = "powershell.exe"
```

**③ 两个关键环境变量（方式 B 就是手动设它们）**

- `PATH` 必须含 `~\.sifli\tools\arm-none-eabi-gcc\14.2.1\bin`
  —— `tools/build/gcc.py` 的 `GetGCCRoot()` **只查 PATH** 找 `arm-none-eabi-gcc.exe`，
  找不到就返回 `None`，然后 `os.path.join(None, ...)` 抛 TypeError。
- `PYTHONPATH` 必须含 `SDK\tools\build`
  —— `SConstruct` 第 9 行是 `from building import *`。
  官方是靠 `tools/export_utils/activate_venv.py` 第 94 行设的。
